# Components and Kubernetes Objects in Percona PostgreSQL Operator

## Overview

When you deploy a PostgreSQL cluster using the Percona PostgreSQL Operator, it automatically creates and manages a comprehensive set of Kubernetes objects. These objects work together to provide a fully functional, highly available PostgreSQL cluster. 

## Custom Resource Definitions(CRD)

The Operator extends the Kubernetes API with the following Custom Resource Definitions, all the CRD uses the API version `apiextensions.k8s.io/v1`.
CRD are used for schema and the end user doesn't need to interact directly with CRD.

## Custom Resources(CR)

Following Custom Resources are used by the end user for defining actions on postgreSQL cluster. All the below custom resources are of version `pgv2.percona.com/v2`.
More details can be found at respective [reference section](https://docs.percona.com/percona-operator-for-postgresql/latest/operator.html)

### 1. `PerconaPGCluster`

Defines Postgres specifications and configurations. Operator uses this `PerconaPGCluster` Custom Resource to process Postgres cluster and configure it accordingly.
When a CR of type `PerconaPGCluster` is created , postgres cluster is created.

**Fields include:**
- Cluster name, PostgreSQL version, image specifications
- Instance configuration (replicas, resources, storage)
- Backup configuration (pgBackRest settings, schedules,storage)
- Proxy configuration (pgBouncer settings)
- Monitoring configuration (PMM integration)
- User and database definitions
- TLS/SSL configuration
- Patroni high-availability settings
- Storage class specifications for volumes

### 2. `PerconaPGBackup`

Defines the backup operations. When you create a `PerconaPGBackup` Custom Resource, the Operator creates a backup of the Postgres.

**Fields include:**
- Backup name, Postgres Cluster Name, pgBackrest repository name
- pgBackRest configurations like type of backup,compression 


### 3. `PerconaPGRestore`

Defines the restore operations. When you create a `PerconaPGRestore` Custom Resource, the Operator restores a Postgres Cluster from an existing backup.

**Fields include:**
- Restore name, Postgres Cluster Name, pgBackrest repository name
- Restore parameters like selecting backup to restore, specific time to restore

### StatefulSets

StatefulSets are used for stateful PostgreSQL components that require stable network identities and persistent storage.

#### 1. PostgreSQL Instance StatefulSet

**Name Pattern:** `<clusterName>-<instanceName>`

**Purpose:** Manages PostgreSQL primary and replica pods with stable identities and ordered deployment.

**Key Features:**
- **Stable Pod Names:** Pods are named `<clusterName>-<instanceName>-0`, `<clusterName>-<instanceName>-1`, etc.
- **Stable Network Identity:** Each pod gets a stable DNS name: `<pod-name>.<service-name>.<namespace>.svc.cluster.local`
- **Ordered Deployment:** Pods are created and terminated in order (0, 1, 2...)
- **Persistent Storage:** Each pod has its own PersistentVolumeClaim for data and WAL

**Pods Contain:**
- PostgreSQL database server
- Patroni (high-availability manager)
- pgBackRest sidecar (for backups)
- Optional: PMM client (for monitoring)
- Optional: Custom sidecar containers

**Interactions:**
- Uses Services for network access
- Mounts PersistentVolumeClaims for data persistence
- References ConfigMaps for PostgreSQL configuration
- References Secrets for credentials and TLS certificates
- Uses ServiceAccount for RBAC

#### 2. pgBackRest Repository Host StatefulSet (if using volume-based backups)

**Name Pattern:** `<clusterName>-repo-<repoName>-<index>`

**Purpose:** Provides a dedicated host for pgBackRest repository storage when using PersistentVolumes instead of cloud storage.

**Key Features:**
- Stores backup data in PersistentVolumes
- Provides network-accessible backup storage
- Can be scaled for redundancy

**Interactions:**
- PostgreSQL pods connect to this StatefulSet for backups
- Uses PersistentVolumeClaims for backup storage
- Exposed via Service for network access

### Deployments

Deployments are used for stateless components that can be scaled horizontally.

#### 1. pgBouncer Deployment

**Name Pattern:** `<clusterName>-pgbouncer`

**Purpose:** Manages pgBouncer connection pooler pods for efficient connection management.

**Key Features:**
- **Stateless:** Can be scaled horizontally (multiple replicas)
- **Load Balancing:** Distributes connections across multiple pgBouncer instances
- **Connection Pooling:** Reduces PostgreSQL connection overhead

**Pods Contain:**
- pgBouncer connection pooler
- pgBouncer configuration sidecar
- Optional: PMM client

**Interactions:**
- Connects to PostgreSQL primary and replica Services
- Uses ConfigMaps for pgBouncer configuration
- Uses Secrets for PostgreSQL connection credentials
- Exposed via Service for application access
- Uses ServiceAccount for RBAC

### Services

Services provide stable network endpoints for accessing PostgreSQL components.

#### 1. PostgreSQL Primary Service

**Name Pattern:** `<clusterName>-ha`

**Purpose:** Provides a stable endpoint to the PostgreSQL primary instance.

**Key Features:**
- **Read-Write Access:** Routes traffic to the current primary instance
- **High Availability:** Automatically updates when failover occurs
- **Selector:** Uses labels to target the current primary pod

**Service Type Options:**
- `ClusterIP` (default): Internal cluster access only
- `LoadBalancer`: External access via cloud load balancer
- `NodePort`: External access via node ports

**Interactions:**
- Used by applications for write operations
- Used by pgBouncer to connect to primary
- Used by replicas for streaming replication
- Referenced in user Secrets for connection strings

#### 2. PostgreSQL Replica Service

**Name Pattern:** `<clusterName>-replica`

**Purpose:** Provides a stable endpoint to PostgreSQL replica instances for read operations.

**Key Features:**
- **Read-Only Access:** Routes traffic to replica instances
- **Load Balancing:** Distributes read queries across multiple replicas
- **Selector:** Uses labels to target replica pods

**Service Type Options:**
- `ClusterIP` (default): Internal cluster access only
- `LoadBalancer`: External access via cloud load balancer
- `NodePort`: External access via node ports

**Interactions:**
- Used by applications for read operations
- Used by pgBouncer for read load balancing
- Referenced in user Secrets for read-only connection strings

#### 3. PostgreSQL Instance Services

**Name Pattern:** `<clusterName>-<instanceName>`

**Purpose:** Provides stable endpoints for individual PostgreSQL instances (used by Patroni for replication).

**Key Features:**
- **Per-Instance Access:** Each instance has its own Service
- **Replication:** Used by Patroni for streaming replication
- **Health Checks:** Used for Patroni leader election

**Interactions:**
- Used by Patroni for replication connections
- Used for instance-specific operations
- Referenced in Patroni configuration

#### 4. pgBouncer Service

**Name Pattern:** `<clusterName>-pgbouncer`

**Purpose:** Provides a stable endpoint for pgBouncer connection pooler.

**Key Features:**
- **Connection Pooling:** Applications connect through this Service
- **Load Balancing:** Distributes connections across pgBouncer pods
- **High Availability:** Multiple pgBouncer pods behind the Service

**Service Type Options:**
- `ClusterIP` (default): Internal cluster access only
- `LoadBalancer`: External access via cloud load balancer
- `NodePort`: External access via node ports

**Interactions:**
- Used by applications as the primary database endpoint
- Routes connections to PostgreSQL primary and replica Services
- Uses ConfigMaps for connection pool configuration

#### 5. pgBackRest Repository Service (if using volume-based backups)

**Name Pattern:** `<clusterName>-repo-<repoName>`

**Purpose:** Provides network access to pgBackRest repository host.

**Interactions:**
- Used by PostgreSQL pods to access backup storage
- Used by backup and restore Jobs

### PersistentVolumeClaims (PVCs)

PVCs provide persistent storage for stateful data.

#### 1. PostgreSQL Data PVCs

**Name Pattern:** `data-<clusterName>-<instanceName>-<podIndex>`

**Purpose:** Stores PostgreSQL data directory (`PGDATA`).

**Key Features:**
- **Persistent:** Data survives pod restarts and rescheduling
- **Per-Pod:** Each PostgreSQL pod has its own data PVC
- **Storage Class:** Configurable storage class for performance/cost optimization
- **Size:** Configurable storage size

**Contains:**
- PostgreSQL data files
- Database files, indexes, tables
- Configuration files managed by Patroni

**Interactions:**
- Mounted by PostgreSQL StatefulSet pods
- Bound to PersistentVolumes by Kubernetes
- Retained on pod deletion (unless finalizer is set)

#### 2. PostgreSQL WAL PVCs

**Name Pattern:** `wal-<clusterName>-<instanceName>-<podIndex>`

**Purpose:** Stores PostgreSQL Write-Ahead Log (WAL) files (optional, can share data volume).

**Key Features:**
- **Optional:** Can be separate from data volume for performance
- **Performance:** Dedicated storage for WAL improves write performance
- **Scaling:** Independent scaling of WAL storage

**Contains:**
- WAL files for transaction logging
- WAL segments for replication

**Interactions:**
- Mounted by PostgreSQL StatefulSet pods
- Used by pgBackRest for WAL archiving
- Used by replicas for streaming replication

#### 3. pgBackRest Repository PVCs

**Name Pattern:** `backup-<clusterName>-repo-<repoName>-<index>`

**Purpose:** Stores backup data when using volume-based backups (instead of cloud storage).

**Key Features:**
- **Backup Storage:** Stores full, incremental, and differential backups
- **WAL Archives:** Stores archived WAL files for point-in-time recovery
- **Scalable:** Can have multiple repository hosts for redundancy

**Contains:**
- pgBackRest backup files
- WAL archive files
- Backup metadata

**Interactions:**
- Mounted by pgBackRest repository StatefulSet
- Accessed by backup and restore Jobs
- Used by PostgreSQL pods for WAL archiving

#### 4. Tablespace PVCs (if custom tablespaces are configured)

**Name Pattern:** `tablespace-<tablespaceName>-<clusterName>-<instanceName>-<podIndex>`

**Purpose:** Provides dedicated storage for PostgreSQL tablespaces.

**Key Features:**
- **Custom Storage:** Allows placing specific tables on different storage
- **Performance:** Can use faster storage for frequently accessed data
- **Flexibility:** Multiple tablespaces per cluster

**Interactions:**
- Mounted by PostgreSQL StatefulSet pods
- Used by PostgreSQL for tablespace storage

### ConfigMaps

ConfigMaps store configuration data that doesn't contain sensitive information.

#### 1. PostgreSQL Configuration ConfigMap

**Name Pattern:** `<clusterName>-pgha-config`

**Purpose:** Stores Patroni and PostgreSQL configuration.

**Contains:**
- Patroni configuration (DCS settings, leader election)
- PostgreSQL dynamic configuration parameters
- Replication settings
- High-availability settings

**Interactions:**
- Mounted by PostgreSQL pods
- Updated by Operator when Custom Resource changes
- Used by Patroni to manage PostgreSQL configuration

#### 2. pgBouncer Configuration ConfigMap

**Name Pattern:** `<clusterName>-pgbouncer-config`

**Purpose:** Stores pgBouncer connection pooler configuration.

**Contains:**
- Connection pool settings
- Database connection mappings
- Pooling mode configuration
- User authentication settings

**Interactions:**
- Mounted by pgBouncer pods
- Used by pgBouncer configuration sidecar
- Updated when Custom Resource changes

#### 3. pgBackRest Configuration ConfigMap

**Name Pattern:** `<clusterName>-pgbackrest-config`

**Purpose:** Stores pgBackRest backup and restore configuration.

**Contains:**
- Repository configurations (S3, GCS, Azure, or volume)
- Backup retention policies
- Compression settings
- Archive settings

**Interactions:**
- Mounted by PostgreSQL pods (pgBackRest sidecar)
- Used by backup and restore Jobs
- Referenced by pgBackRest repository host

#### 4. Init SQL ConfigMap (if initSQL is configured)

**Name Pattern:** Custom name specified in Custom Resource

**Purpose:** Stores SQL scripts to execute during database initialization.

**Contains:**
- SQL scripts for database setup
- Schema creation scripts
- Initial data scripts

**Interactions:**
- Read by PostgreSQL during initialization
- Executed once during cluster creation

### Secrets

Secrets store sensitive information like passwords, certificates, and connection strings.

#### 1. PostgreSQL User Secrets

**Name Pattern:** `<clusterName>-pguser-<userName>`

**Purpose:** Stores PostgreSQL user credentials and connection information.

**Contains:**
- `username`: PostgreSQL username
- `password`: PostgreSQL password
- `host`: Database host (Service name)
- `port`: Database port
- `dbname`: Database name (if specified)
- `uri`: PostgreSQL connection URI
- `jdbc-uri`: JDBC connection string

**Interactions:**
- Created automatically for each user in Custom Resource
- Used by applications to connect to PostgreSQL
- Referenced in deployment configurations
- Updated when passwords change

#### 2. PostgreSQL Superuser Secret

**Name Pattern:** `<clusterName>-pguser-postgres`

**Purpose:** Stores the PostgreSQL superuser (`postgres`) credentials.

**Contains:**
- Superuser credentials
- Connection information

**Interactions:**
- Used by Operator for administrative operations
- Used by Patroni for cluster management
- Used by backup/restore operations

#### 3. Replication Secret

**Name Pattern:** `<clusterName>-pguser-crunchyrepl`

**Purpose:** Stores credentials for PostgreSQL replication user.

**Contains:**
- Replication user credentials
- Used for streaming replication between primary and replicas

**Interactions:**
- Used by Patroni for replication setup
- Used by replica pods to connect to primary
- Used for WAL streaming

#### 4. TLS/SSL Secrets

**Name Patterns:**
- `<clusterName>-cluster-cert` (cluster TLS certificate)
- `<clusterName>-replication-cert` (replication TLS certificate)
- Custom TLS secrets (if specified)

**Purpose:** Stores TLS certificates and keys for encrypted connections.

**Contains:**
- TLS certificates (`.crt` files)
- Private keys (`.key` files)
- Certificate authority certificates

**Interactions:**
- Mounted by PostgreSQL pods for encrypted connections
- Used for client-to-database encryption
- Used for replication stream encryption
- Used by pgBouncer for encrypted connections

#### 5. pgBackRest Repository Secrets

**Name Pattern:** Custom name (for S3/GCS/Azure credentials)

**Purpose:** Stores credentials for cloud backup storage.

**Contains:**
- AWS access keys (for S3)
- GCS service account keys (for Google Cloud Storage)
- Azure storage account keys (for Azure Blob Storage)

**Interactions:**
- Used by pgBackRest for cloud backup operations
- Referenced in pgBackRest configuration
- Used by backup and restore Jobs

#### 6. PMM Secret (if PMM monitoring is enabled)

**Name Pattern:** Custom name specified in Custom Resource

**Purpose:** Stores PMM server password for monitoring integration.

**Contains:**
- PMM server password

**Interactions:**
- Used by PMM client sidecar in PostgreSQL pods
- Used for authenticating to PMM server

### Jobs

Jobs are used for one-time or on-demand operations.

#### 1. Backup Jobs

**Name Pattern:** `<clusterName>-backup-<timestamp>` or custom name

**Purpose:** Executes on-demand backup operations.

**Key Features:**
- **On-Demand:** Created when you create a `PerconaPGBackup` Custom Resource
- **Full/Incremental:** Supports full, incremental, and differential backups
- **Ephemeral:** Job is deleted after completion

**Interactions:**
- Uses pgBackRest configuration from ConfigMap
- Accesses PostgreSQL data via mounted volumes or network
- Writes backups to repository (cloud storage or volume)
- Uses Secrets for repository credentials

#### 2. Restore Jobs

**Name Pattern:** `<clusterName>-restore-<timestamp>` or custom name

**Purpose:** Executes restore operations from backups.

**Key Features:**
- **On-Demand:** Created when you create a `PerconaPGRestore` Custom Resource
- **Point-in-Time Recovery:** Supports restoring to specific timestamps
- **Cluster Initialization:** Can initialize new clusters from backups

**Interactions:**
- Reads backups from repository
- Restores data to PostgreSQL data volumes
- Uses pgBackRest configuration from ConfigMap
- Uses Secrets for repository credentials

### CronJobs

CronJobs are used for scheduled, recurring operations.

#### 1. Scheduled Backup CronJobs

**Name Pattern:** `<clusterName>-backup-<repoName>-<backupType>-<schedule>`

**Purpose:** Automatically executes backups on a schedule.

**Key Features:**
- **Scheduled:** Runs backups based on cron schedule
- **Full Backups:** Scheduled full backups
- **Incremental Backups:** Scheduled incremental backups
- **Differential Backups:** Scheduled differential backups

**Interactions:**
- Creates Backup Jobs on schedule
- Uses same configuration as manual backups
- Can be paused/resumed via Custom Resource

### ServiceAccounts

ServiceAccounts provide identity for pods and enable RBAC.

#### 1. PostgreSQL ServiceAccount

**Name Pattern:** `<clusterName>-postgres`

**Purpose:** Provides identity for PostgreSQL pods.

**Permissions:**
- Access to ConfigMaps and Secrets
- Pod management (for Patroni operations)
- Service management (for leader election)

**Interactions:**
- Used by PostgreSQL StatefulSet pods
- Referenced in RoleBindings for RBAC
- Allows Patroni to manage cluster state

#### 2. pgBouncer ServiceAccount

**Name Pattern:** `<clusterName>-pgbouncer`

**Purpose:** Provides identity for pgBouncer pods.

**Permissions:**
- Access to ConfigMaps and Secrets
- Service access

**Interactions:**
- Used by pgBouncer Deployment pods
- Referenced in RoleBindings for RBAC

#### 3. pgBackRest ServiceAccount

**Name Pattern:** `<clusterName>-pgbackrest`

**Purpose:** Provides identity for backup and restore operations.

**Permissions:**
- Access to backup storage
- Access to PostgreSQL data volumes
- Access to Secrets for repository credentials

**Interactions:**
- Used by backup and restore Jobs
- Used by pgBackRest sidecar containers

### Roles and RoleBindings

Roles and RoleBindings implement RBAC for secure access control.

#### 1. PostgreSQL Role

**Name Pattern:** `<clusterName>-postgres`

**Purpose:** Defines permissions for PostgreSQL pods.

**Permissions:**
- Read ConfigMaps and Secrets
- Update ConfigMaps (for Patroni configuration)
- Get, list, watch, update Pods (for Patroni leader election)
- Get, list, watch Services (for service management)

**Interactions:**
- Bound to PostgreSQL ServiceAccount via RoleBinding
- Enables Patroni to manage cluster state

#### 2. pgBouncer Role

**Name Pattern:** `<clusterName>-pgbouncer`

**Purpose:** Defines permissions for pgBouncer pods.

**Permissions:**
- Read ConfigMaps and Secrets
- Access Services

**Interactions:**
- Bound to pgBouncer ServiceAccount via RoleBinding

### PodDisruptionBudgets (PDBs)

PDBs ensure high availability during voluntary disruptions.

#### 1. PostgreSQL PodDisruptionBudget

**Name Pattern:** `<clusterName>-postgres`

**Purpose:** Ensures minimum number of PostgreSQL pods remain available during disruptions.

**Key Features:**
- **Min Available:** Ensures at least N pods are available
- **High Availability:** Prevents all pods from being disrupted simultaneously
- **Maintenance:** Allows safe node maintenance

**Interactions:**
- Applied to PostgreSQL StatefulSet pods
- Works with Kubernetes scheduler during node drains
- Ensures primary and at least one replica remain available

#### 2. pgBouncer PodDisruptionBudget

**Name Pattern:** `<clusterName>-pgbouncer`

**Purpose:** Ensures minimum number of pgBouncer pods remain available.

**Interactions:**
- Applied to pgBouncer Deployment pods
- Ensures connection pooling remains available during maintenance

## Component Interactions

### Data Flow

1. **Application → pgBouncer Service → pgBouncer Pods → PostgreSQL Services → PostgreSQL Pods**
   - Applications connect through pgBouncer for connection pooling
   - pgBouncer routes connections to primary (writes) or replicas (reads)

2. **Primary → Replicas (Streaming Replication)**
   - Primary streams WAL to replicas via instance Services
   - Patroni manages replication configuration

3. **PostgreSQL Pods → pgBackRest Repository (Backups)**
   - pgBackRest sidecar in PostgreSQL pods performs backups
   - Backups stored in cloud storage (S3/GCS/Azure) or volume-based repository

### Control Flow

1. **Custom Resource → Operator → Kubernetes Objects**
   - Operator watches Custom Resources
   - Creates/updates/deletes Kubernetes objects based on desired state
   - Continuously reconciles actual state with desired state

2. **Patroni → Kubernetes API (Leader Election)**
   - Patroni uses Kubernetes as distributed consensus store
   - Manages leader election and failover
   - Updates Service endpoints when primary changes

3. **Backup/Restore Custom Resources → Operator → Jobs**
   - Operator creates Jobs for backup/restore operations
   - Jobs execute pgBackRest commands
   - Operator monitors Job status and updates Custom Resource

### Storage Flow

1. **PostgreSQL Data:**
   - Data written to data PVC
   - WAL written to WAL PVC (if separate)
   - Patroni manages data consistency

2. **Backups:**
   - pgBackRest reads from data and WAL volumes
   - Backups written to repository (cloud or volume)
   - WAL archived continuously for point-in-time recovery

3. **Restores:**
   - Restore Jobs read from repository
   - Data restored to data volumes
   - Cluster initialized from restored data

## High Availability Architecture

### Primary-Replica Setup

- **Primary:** One read-write instance (leader)
- **Replicas:** Multiple read-only instances (followers)
- **Failover:** Automatic promotion of replica to primary on failure
- **Zero Data Loss:** WAL-based replication ensures no data loss

### Pod Distribution

- **Anti-Affinity:** Pods distributed across different nodes
- **PodDisruptionBudgets:** Ensure minimum availability during maintenance
- **Node Failures:** Pods automatically rescheduled to healthy nodes

### Service Failover

- **Primary Service:** Automatically routes to new primary after failover
- **Replica Service:** Load balances across available replicas
- **Health Checks:** Services only route to healthy pods

## Summary

The Percona PostgreSQL Operator creates a comprehensive set of Kubernetes objects that work together to provide:

- **High Availability:** StatefulSets, Services, and Patroni ensure cluster resilience
- **Data Persistence:** PersistentVolumeClaims ensure data survives pod restarts
- **Backup and Recovery:** Jobs, CronJobs, and pgBackRest provide backup capabilities
- **Connection Management:** pgBouncer Deployment and Service provide connection pooling
- **Security:** Secrets, TLS certificates, and RBAC ensure secure operations
- **Monitoring:** Integration with PMM for observability
- **Automation:** Operator continuously reconciles desired and actual state

All these components are automatically created, configured, and managed by the Operator based on your Custom Resource definitions, eliminating the need for manual Kubernetes object management.
