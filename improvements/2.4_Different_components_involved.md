# Components and Kubernetes Objects in Percona PostgreSQL Operator

When you deploy a PostgreSQL cluster using the Percona PostgreSQL Operator, it automatically creates and manages a comprehensive set of Kubernetes objects. These objects work together to provide a fully functional, highly available PostgreSQL cluster. 

Below detailed information on the resources are provided.


## Custom Resource Definitions(CRD)

The Operator extends the Kubernetes API with the following Custom Resource Definitions, all the CRD uses the API version `apiextensions.k8s.io/v1`.
CRD are used for schema and the end user doesn't need to interact directly with CRD.

## Custom Resources(CR)

Following Custom Resources are used by the end user for defining actions on postgreSQL cluster. All the below custom resources are of version `pgv2.percona.com/v2`.
More details can be found at respective [reference section](https://docs.percona.com/percona-operator-for-postgresql/latest/operator.html)

### 1. `PerconaPGCluster`

Defines Postgres specifications and configurations. Operator uses this `PerconaPGCluster` Custom Resource to process Postgres cluster and configure it accordingly.
When a CR of type `PerconaPGCluster` is created , postgres cluster is created.

**Fields include:**
- Cluster name, PostgreSQL version, image specifications
- Instance configuration (replicas, resources, storage)
- Backup configuration (pgBackRest settings, schedules,storage)
- Proxy configuration (pgBouncer settings)
- Monitoring configuration (PMM integration)
- User and database definitions
- TLS/SSL configuration
- Patroni high-availability settings
- Storage class specifications for volumes

[Refer](https://docs.percona.com/percona-operator-for-postgresql/latest/operator.html) for all the fields

### 2. `PerconaPGBackup`

Defines the backup operations. When you create a `PerconaPGBackup` Custom Resource, the Operator creates a backup of the Postgres.

**Fields include:**
- Backup name, Postgres Cluster Name, pgBackrest repository name
- pgBackRest configurations like type of backup,compression 

[Refer](https://docs.percona.com/percona-operator-for-postgresql/latest/backup-resource-options.html) for all the fields

### 3. `PerconaPGRestore`

Defines the restore operations. When you create a `PerconaPGRestore` Custom Resource, the Operator restores a Postgres Cluster from an existing backup.

**Fields include:**
- Restore name, Postgres Cluster Name, pgBackrest repository name
- Restore parameters like selecting backup to restore, specific time to restore

[Refer](https://docs.percona.com/percona-operator-for-postgresql/latest/restore-options.html) for all the fields

### 4. `PerconaPGUpgrade`

Used to upgrade major version of Postgres

**Fields include**
- Postgres Cluster Name
- PostgreSQL Versions Pre-Upgrade and Post-Upgrade
- Image details of Postgres,PgBouncer,pgBackrest Post-Upgrade

## Core Kubernetes Objects used by Operator

### 1. PostgreSQL instances[StatefulSet]

StatefulSets are used for each instance of stateful PostgreSQL components that require stable network identities and persistent storage. Each instance of a replica has a statefulset.

**Name Pattern:** `<clusterName>-<instanceName>-<hash>`
Where `<hash>` is a 4-character alphanumeric suffix (e.g., `b5mr`, `a3k9`).

Example:
```yaml
  # For cluster of name `cluster1`
  - name: primary
    replicas: 1
    ...
  - name: replica
    replicas: 2
```
This will create following statefulsets:
1. cluster1-primary-<4-character-hash>
2. cluster1-secondary-<4-character-hash>
3. cluster1-secondary-<4-character-hash>

**Purpose:** Manages PostgreSQL primary and replica pods with stable identities and ordered deployment.

Pod contains following containers:

**Init Containers:**
1. `database-init`: Copies and sets the appropriate permissions for certain scripts and binaries needed for database using `install` linux command. Container runs this [script](https://github.com/percona/percona-postgresql-operator/blob/v2.8.2/build/postgres-operator/init-entrypoint.sh)
2. `postgres-startup`: Prepares and validates checks prior to Postgres startup. Following are some of the actions
 - Validates Postgres Version 
 - Checks whether required directories and files (directories such as pgdata, spool, and pgBackRest. files such as postgresql.conf) exist. If not, they are created and appropriate links are set up based on the configuration. Directory permissions and ownership are verified and corrected if necessary.
 More details can be found [here](https://github.com/percona/percona-postgresql-operator/blob/main/internal/postgres/config.go)
3. `nss-wrapper-init`: Configures [NSS](https://man7.org/linux/man-pages/man5/nsswitch.conf.5.html) wrapper. This helps in running container when container is run with arbitrary user ids using [security context](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/) in cases like Openshift. 
PostgreSQL is configured to run as the postgres user, and if the runtime UID does not match, it can cause issues. With the NSS configuration in the container, nss_wrapper adds an entry like postgres:x:<user-id>:... to a separate passwd file, which is a copy of /etc/passwd with this additional entry. A similar process is performed for the group entry.


**Sidecar Containers:** Each PostgreSQL contains following containers

1. `database` : Actual Database container. Patroni is running inside the database container.
2. `replication-cert-copy`: Monitors replication certificates for changes at 5-second intervals and triggers a PostgreSQL reload without restarting the database process when changes are detected.
3. `pgbackrest-config`: Monitors pgbackrest configurations and certificates for changes at 5-second intervals and triggers a pgbackrest reload when changes are detected.
4. `pgbackrest`: pgBackrest container for backup and restore
5. `pmm-client`(optional): Captures Database metrics and pushes them to PMM Server

Optionally there can be other custom init or side car containers.


**Interactions:**
- Uses Services for network access
- Mounts PersistentVolumeClaims for data persistence
- References ConfigMaps for PostgreSQL configuration
- References Secrets for credentials and TLS certificates
- Uses ServiceAccount for RBAC

#### 2. pgBackRest Repository Host (if using volume-based backups) [StatefulSet]

**Name Pattern:** `<clusterName>-repo-<host>`

**Purpose:** Provides a dedicated host for pgBackRest repository storage when using PersistentVolumes.

**Key Features:**
- Stores backup data in PersistentVolumes
- Provides network-accessible backup storage
- Can be scaled for redundancy

**Sidecar Containers:** : Pods contain following side car containers:

1. `pgbackrest`: pgBackrest container
2. `pgbackrest-config`: Monitors pgbackrest configurations and certificates for changes at 5-second intervals and triggers a pgbackrest reload when changes are detected.

**Interactions:**
- PostgreSQL pods connect to this StatefulSet for backups
- Uses PersistentVolumeClaims for backup storage
- Exposed via Service for network access


#### 3. pgBouncer [Deployment]

**Name Pattern:** `<clusterName>-pgbouncer`

**Purpose:** Manages pgBouncer connection pooler pods for efficient connection management.

**Key Features:**
- **Stateless:** Can be scaled horizontally (multiple replicas)
- **Load Balancing:** Distributes connections across multiple pgBouncer instances
- **Connection Pooling:** Reduces PostgreSQL connection overhead

**Pods Contain:**
- pgBouncer connection pooler
- pgBouncer configuration sidecar
- Optional: PMM client

**Sidecar Containers:** : Pods contain following side car containers:

1. `pgBouncer`: pgBouncer container
2. `pgBouncer-config`: Monitors pgBouncer configurations for changes at 5-second intervals and triggers a pgBouncer reload when changes are detected.

Optionally there can be other custom side car containers.


**Interactions:**
- Connects to PostgreSQL primary and replica Services
- Uses ConfigMaps for pgBouncer configuration
- Uses Secrets for PostgreSQL connection credentials
- Exposed via Service for application access
- Uses ServiceAccount for RBAC


#### 4. operator[Deployment]

**Name Pattern:** percona-postgresql-operator (Can be changed)

**Purpose:** Reconciles custom resources like PerconaPGCluster,PerconaPGBackup,PerconaPGRestore,PerconaPGUpgrade and other objects like secrets,configmaps,services to ensure cluster is working as expected.

 Pod contain only one container but it is possible to run custom init or side car containers like a standard Deployment object in kubernetes.

**Interactions:**
- Pretty much everything connected to the Postgres Cluster.

### 5. Services / Endpoints

Services provide stable network endpoints for accessing PostgreSQL components.By default all the services are of type `clusterIP`,however they can be configured.
Following are the services/endpoints created and managed by the operator:

5.1. **<cluster-name>-ha**: Selector-less Service used by Patroni for HA leader routing. Patroni updates the respective Endpoints to point to the currently elected Postgres leader (the operator creates/patches the Service and sets labels/ownership).

5.2. **<cluster-name>-ha-config**: Uses Endpoints to store the DCS in the annotation field. A Headless Service object is used to avoid cleaning up the endpoint as kubernetes will remove the endpoints without an associated service. More details can be found [here](https://github.com/patroni/patroni/blob/v4.1.0/docs/kubernetes.rst)

5.3. **<cluster-name>-pgbouncer**: Service to expose pgBouncer pods. It uses the following label selector to determine the set of Pods that receive traffic.
Uses the following selector
```
    postgres-operator.crunchydata.com/cluster: <cluster-name>
    postgres-operator.crunchydata.com/role: pgbouncer
```

5.4. **<cluster-name>-primary**:  A Headless Service to expose Postgres Primary Pod. Service essentially redirects to the service <cluster-name>-ha which is managed with Patroni. This seperate service helps to have consistent and easily recognizable service name/identity and also decouple from any patroni naming conventions.

5.5. **<cluster-name>-replicas**: Service to expose Postgres replica pods. It uses the following label selector to determine the set of Pods that receive traffic.
```
    postgres-operator.crunchydata.com/cluster: <cluster-name>
    postgres-operator.crunchydata.com/role: replica
```

5.6. **<cluster-name>-pods**: A Headless Service with label selector to seelct all the pods of the Postgres cluster. This is helpful in providing stable DNS entries even if the pods are not ready.

There will be endpoint slices which will be associated with the endpoints created automatically by the k8s control plane.

### 7.ConfigMaps

ConfigMaps store configuration data that doesn't contain sensitive information.

#### 7.1. PostgreSQL Cluster Configuration ConfigMap

**Name Pattern:** `<clusterName>-config`

**Purpose:** Stores Patroni clusterwide configuration. Mounted to database container or all instance pods.

**Options include:**
- Patroni configuration (DCS settings, leader election)
- PostgreSQL dynamic configuration parameters
- Replication settings
- High-availability settings
- If DCS is stored in configmaps or endpoints
- If watchdog needs to be used(Needs priviliged containers)

This is a shared configmap and all postgreSQL pods mount this as a volume. This is referenced by Patroni to manage PostgreSQL configurations.

**This config map is managed by the postgres-operator and it is advised not to modify the data in the configmap.For any custom usecase, if the configmap needs to be overriden add the annotation `pgv2.percona.com/override-config=true` otherwise operator will overwrite any config changes made** 

#### 7.2. PostgreSQL instance ConfigMap

**Name Pattern:** `<clusterName>-<instance-name>-<hash>-config`

**Purpose:** Per instance patroni configuration. Mounted to database container of the specific instance.

**Contains:**
- Backup methods
- WAL directory

**This config map is managed by the postgres-operator and it is advised not to modify the data in the configmap.For any custom usecase, if the configmap needs to be overriden add the annotation `pgv2.percona.com/override-config=true` otherwise operator will overwrite any config changes made** 


#### 7.3. pgBackRest Configuration ConfigMap

**Name Pattern:** `<clusterName>-pgbackrest-config`

**Purpose:** Stores [pgBackRest configuration](https://pgbackrest.org/configuration.html). It’s mounted into database,pgBackRest,pgbackrest-config containers of the postgres pods under /etc/pgbackrest/conf.d so backups/restores and repo/instance pgBackRest sidecars run with consistent settings.

This configmap is also mounted for the job created when a `PerconaPGBackup` object is created

**Contains:**
- Repository configurations (S3, GCS, Azure, or volume)
- Log Level
- Certificate locations

**This config map is managed by the postgres-operator and it is advised not to modify the data in the configmap.For any custom usecase, if the configmap needs to be overriden add the annotation `pgv2.percona.com/override-config=true` otherwise operator will overwrite any config changes made** 

#### 7.4. pgBouncer Configuration ConfigMap

**Name Pattern:** `<clusterName>-pgbouncer`

**Purpose:** Contains [pgBouncer configurations](https://www.pgbouncer.org/config.html). Config map is mounted to pgbouncer pods.

**This config map is managed by the postgres-operator and it is advised not to modify the data in the configmap.For any custom usecase, if the configmap needs to be overriden add the annotation `pgv2.percona.com/override-config=true` otherwise operator will overwrite any config changes made** 


#### 7.5. Init SQL ConfigMap (present only if databaseInitSQL is configured)

**Name Pattern:** Custom name specified in Custom Resource

**Purpose:** Stores SQL scripts to execute during database initialization.

**Contains:**
- SQL scripts for database setup
- Schema creation scripts
- Initial data scripts

**Interactions:**
- Read by PostgreSQL during initialization
- Executed once during cluster creation

[More details present](https://docs.percona.com/percona-operator-for-postgresql/latest/operator.html#databaseinitsqlname)

### 8. Secrets

Secrets store sensitive information like passwords, certificates.

#### 8.1. PostgreSQL User Secrets

**Name Pattern:** `<clusterName>-pguser-<userName>` unless configured by [spec.users.secretName](https://docs.percona.com/percona-operator-for-postgresql/latest/operator.html#userssecretname).
Created automatically for each user in `spec.users`. By default username with <cluster-name> is created.

**Purpose:** Stores PostgreSQL user credentials and connection information. Check [doc](https://docs.percona.com/percona-operator-for-postgresql/latest/users.html) for more information.

**Contains:**
- `username`: PostgreSQL username
- `password`: PostgreSQL password
- `host`: Database primary host (Service name)
- `port`: Database port
- `dbname`: Database name (if specified)
- `uri`: Connection URI for postgres primary
- `jdbc-uri`: JDBC connection string for the primary
- `verifier`: A hashed representation of the password using SCRAM-SHA-256
- `pgbouncer-host`: PG Bouncer endpoint
- `pgbouncer-jdbc-uri`: JDBC connection string for postgres primary
- `pgbouncer-port`: pgbouncer port
- `pgbouncer-uri`: Connection URI for pgbouncer


#### 8.2. TLS/SSL Secrets

##### 8.2.2 Root Certificate Secret

**Name Pattern:** `<clusterName>-ca-cert` unless configured by [spec.secrets.customRootCATLSSecret.name](https://docs.percona.com/percona-operator-for-postgresql/latest/operator.html#secretscustomrootcatlssecretname)

**Purpose:** Contains Root certificate to sign leaf certificates.


#### 8.2.3. Certificate for Client to Postgres Server

**Name Pattern:** `<clusterName>-cluster-cert` unless configured by [secrets.customTLSSecret.name](https://docs.percona.com/percona-operator-for-postgresql/latest/operator.html#secretscustomtlssecretname)

**Purpose:** Certificate for Postgres server and client communication via TLS

#### 8.2.4 Per Instance Certificate

**Name Pattern**: `<clusterName>-<instance-name>-<hash>-certs`

**Purpose:** Used by Patroni and PGBackrest for secure communication between instances. Patroni uses it for Rest API and pgbackrest for the server.

#### 8.2.5. PMM Secrets(if PMM monitoring is enabled)

**Name Pattern:** Custom name as specified in the path `spec.pmm.secret`

**Purpose:** Stores Token for PMM client side car container to PMM Server authentication. [PMM](https://www.percona.com/software/database-tools/percona-monitoring-and-management) monitors database. More information can be found [here](https://docs.percona.com/percona-operator-for-postgresql/latest/monitoring.html)


#### 8.2.6 Secret for S3 or S3 compatible buckets for custom extensions

**Name Pattern:** Custom name as specified in the path `spec.extensions.storage.secret.name`

**Purpose:** Secret stored for custom extension object storage authentication.retrieve custom extension tar bundle are retrieved from this location. More details can be found [here](https://docs.percona.com/percona-operator-for-postgresql/2.8.0/custom-extensions.html)



### 9. Jobs

Jobs are used for one-time or on-demand operations like Backup and restore.

#### 9.1. Backup Jobs

**Name Pattern:** `<clusterName>-backup-<hash>` for scheduled backup or custom name for on-demand backup

**Purpose:** Backup jobs are created by the operator when a `PerconaPGBackup` object is created. Job triggers pgbackrest with appropriate settings to perform a postgres backup.


#### 9.2. Restore Jobs

**Name Pattern:** `<clusterName>-pgbackrest-restore` 

**Purpose:** Restore jobs are created the operator when a `PerconaPGRestore` object is created. Job triggers pgbackrest with appropriate settings to restore postgres cluster using existing backups.

#### 9.3 Upgrade Jobs

When a PerconaPGUpgrade object is created for major version upgrade, following jobs are created:

1. <PerconPGUpgrade-name>-pgdata: This job does the actual upgrade and checks
2. <PerconaPGUpgrade-name>-<cluster-name>-<instance-name>-<hash>: This job verifies whether the pgdata directory associated with the pre-upgrade version is still in use. If it is not in use, the job cleans up the corresponding pre-upgrade pgdata directory.

### 10. RBAC(ServiceAccounts,Role,ClusterRole,RoleBinding,ClusterRoleBinding)

ServiceAccounts provide identity for pods and enable RBAC.Roles and RoleBindings implement RBAC for secure access control. Operator uses `Role` and `Rolebinding` for [namespace wide mode](2.1.6.1_namespace_modes.md#namespace-scoped-deployment) and uses `ClusterRole` and `ClusterRoleBinding` for the [cluster wide mode](2.1.6.1_namespace_modes.md#cluster-wide-deployment).
All the objects ServiceAccount,Role/ClusterRole,ClusterRole/ClusterRoleBinding use the same name

#### 10.1. Operator RBAC

**Name Pattern:** : `percona-postgresql-operator` unless customixed by the user

 **Purpose:**: Attached to percona operator deployment. Service account associates with a Role or a ClusterRole to perform reconiciliation tasks.
 [Role](https://github.com/percona/percona-postgresql-operator/blob/41a695ae2813345fa49a753d266b41ece763a3bb/deploy/rbac.yaml#L6)
 [ClusterRole](https://github.com/percona/percona-postgresql-operator/blob/95ecfe0fc69cd3eb5ab66176778b4a1bc6a51074/deploy/cw-rbac.yaml#L6)

#### 10.2. PostgreSQL instances ServiceAccount

**Name Pattern:** `<clusterName>-instance`

**Purpose:** This is created by the operator automatically. Associated with the postgres pods. Mainly needed for Patroni to manage leader election process and for the restore job created while restoring a postgres cluster.

### 11. PodDisruptionBudgets (PDBs)

[PDB](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/#pod-disruption-budgets) ensure high availability even  during voluntary disruptions.

#### 1. PostgreSQL PodDisruptionBudget

**Name Pattern:** `<clusterName>-pgbouncer`

**Purpose:** Ensures minimum number of pgBouncer pods remain available even during disruptions. By default it is ensured to have atleast one pgBouncer pod running.


#### 2. pgBouncer PodDisruptionBudget

**Name Pattern:** `<clusterName>-set-<instance-name>`

**Purpose:** Ensures minimum number of instances remain available even during disruptions.By default it is ensured to have atleast one pod is running per instance configuration.

## Component Interactions

### Data Flow

1. **Application → pgBouncer Service → pgBouncer Pods → PostgreSQL Services → PostgreSQL Pods**
   - Applications connect through pgBouncer for connection pooling
   - pgBouncer routes connections to primary (writes) or replicas (reads)

2. **Primary → Replicas (Streaming Replication)**
   - Primary streams WAL to replicas via instance Services
   - Patroni manages leader and DCS via Endpoints
