# Understanding Kubernetes Operators

## What is a Kubernetes Operator?

A Kubernetes Operator is a method of packaging, deploying, and managing a Kubernetes application. It extends the Kubernetes API to create, configure, and manage instances of complex applications on behalf of a Kubernetes user.

At its core, an Operator is a custom controller that uses Custom Resources(CR) to manage applications and their components. Operators follow Kubernetes principles, notably the control loop pattern, where they continuously observe the state of the system and take actions to move the current state closer to the desired state.

Operators are particularly valuable for stateful applications like databases, which require complex lifecycle management, including initialization, scaling, backups, updates, disaster recovery etc.

## How Custom Resources, Custom Resource Definitions, and Operator Deployment are Connected

The relationship between Custom Resources (CRs), Custom Resource Definitions (CRDs), and Operator deployment forms the foundation of how Operators work in Kubernetes:

### Custom Resource Definition (CRD)

A **Custom Resource Definition** is a schema that defines a new type of resource in Kubernetes. It tells Kubernetes:
- What fields the custom resource will have
- What types of values those fields can contain
- How the resource should be validated

For example, a PostgreSQL Operator might define a CRD called `PostgreSQLCluster` with fields like `replicas`, `storageSize`, `postgresVersion`, etc.

### Custom Resource (CR)

A **Custom Resource** is an instance of a CRD. It represents a specific deployment of your application. When you create a Custom Resource, you're essentially declaring your desired state for that application.

For instance, you might create a Custom Resource named `my-postgres-cluster` that specifies you want a PostgreSQL cluster with 3 replicas, 100GB of storage, and PostgreSQL version 16.

### Operator Deployment

The **Operator** itself is deployed as a standard Kubernetes Deployment. It runs as a Pod (or set of Pods) in your cluster and contains the controller logic that:
1. Watches for Custom Resources of the type defined by the CRD
2. Reads the desired state from the Custom Resource
3. Compares it with the current state of the cluster
4. Takes actions to reconcile any differences

Here's how these components work together:

1. Custom Resource Definition(CRD) : Defines the schema, has details like what fields are allowed along with rules if any. Once added to Kubernetes, a new resource type(Custom Resource) is available for the users.
2. Custom Resource (CR) : Each instance of Custom Resource has values for the schema and defines the desired state
3. Operator: Operator is a custom controller to manage the custom resource. Operator constantly reconciles the custom resource and any associated kubernetes objects to run the logic defined and manage application(s).



**Example workflow:**

1. **CRD Installation**: The Operator's CRD is installed first, which registers `PostgreSQLCluster` as a new resource type in the Kubernetes API.

2. **Operator Deployment**: The Operator Pod is deployed, which starts watching for `PostgreSQLCluster` resources.

3. **Custom Resource Creation**: A user creates a Custom Resource YAML file and applies it

4. **Reconciliation**: The Operator detects the new Custom Resource, reads its specification, and creates the necessary Kubernetes resources (StatefulSets, Services, ConfigMaps, Secrets, etc.) to bring the PostgreSQL cluster into existence.

5. **Continuous Monitoring**: The Operator continuously monitors both the Custom Resource and the actual cluster state, making adjustments whenever they diverge.

## Why Using Operators Can Be Beneficial

### 1. Automation and Reduced Operational Overhead

For example: If you want to run PostgresSQL cluster on Kubernetes from scratch, following tasks needs to be done

- Create a StatefulSet for PostgreSQL pods
- Create a Service for database access
- Create PersistentVolumeClaims for data storage
- Create ConfigMaps for configuration
- Create Secrets for credentials
- Manually configure replication
- Set up backup jobs
- Configure monitoring
- ... 

With an operator, you define database specifications in the custom resource and operator takes care of the rest. This leads to reduced Human errors.

### 2. Day-2 Operations

Operators automate repetitive and complex operational tasks that would otherwise require manual intervention or custom scripting:

For example in percona postgress operator:
- **Self-Healing**: Automatically detect and recover from failures (pod crashes, node failures, network issues)
- **Backup Automation**: Schedule and execute backups without manual intervention
- **Update Management**: Handle rolling updates and version upgrades safely
- ...

Operators bring significant advantages when managing complex applications, especially stateful services like databases, in Kubernetes.

### 3.Consistency and Best Practices

Operators embed domain expertise and best practices into automation, enabling customization when needed.

Operators are built keeping following things in mind: 
- **Proven Configurations**: Operators are built by experts who understand the application's requirements
- **Security Hardening**: Default configurations follow security best practices
- **Performance Optimization**: Operators apply performance tuning based on industry standards
- **High Availability**: Built-in support for replication, failover, and disaster recovery
- **Compliance**: Operators can enforce compliance requirements automatically


Example: Default configurations ensure that PostgreSQL pods are not scheduled on the same underlying host.

### 4. Observability

Operators integrate monitoring and observability directly into the application lifecycle:

- **Health Monitoring**: Built-in health checks and status reporting
- **Metrics Collection**: Automatic integration with monitoring systems
- **Event Logging**: Comprehensive logging of all operations
- **Status Reporting**: Clear visibility into the current state of the application

Example: Percona Postgres Operator continuously monitors database health. Detailed Postgress metrics are captured in Percona Monitoring and Management(PMM) with easy configuration.


### 5. **Multi-Cloud and Portability**

Operators make applications portable across different Kubernetes environments:

- **Cloud Agnostic**: Works on any Kubernetes cluster (AWS EKS, GCP GKE, Azure AKS, on-premises, etc)
- **Consistent Experience**: Same management interface regardless of underlying infrastructure
- **Easy Migration**: Move applications between environments by applying the same Custom Resource



## Conclusion

Kubernetes Operators represent a paradigm shift in how we manage complex applications in Kubernetes. By combining Custom Resource Definitions, Custom Resources, and intelligent controllers, Operators provide a powerful way to automate, simplify, and standardize the management of stateful applications like databases.

For database administrators and DevOps engineers working with PostgreSQL in Kubernetes, Operators like the Percona Kubernetes PostgreSQL Operator eliminate much of the complexity and risk associated with manual database management, allowing teams to focus on building applications rather than managing infrastructure.
