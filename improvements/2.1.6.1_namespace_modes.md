# Percona Operator for PostgreSQL Single-namespace and Multi-namespace deployment Modes

The Percona Operator for PostgreSQL supports two distinct deployment patterns that determine how the operator manages PostgreSQL clusters across Kubernetes namespaces:

* **Namespace-scoped deployment** - One operator instance per Kubernetes namespace(Recommended)
* **Cluster-wide deployment** - One operator instance managing clusters across multiple namespaces

This document provides details on both deployment modes, their underlying Kubernetes mechanisms, configuration requirements, and operational considerations.

## Overview

### Namespace-Scoped Deployment

In namespace-scoped mode, each operator instance is confined to a single Kubernetes namespace. The operator uses Kubernetes `Role` and `RoleBinding` resources, which are namespace-scoped, limiting its permissions and watch scope to that specific namespace. **This is the default and recommended deployment pattern**.

![image](./namespace-mode.png)

**Key Characteristics:**
- Uses `Role` and `RoleBinding` (namespace-scoped RBAC) . https://github.com/percona/percona-postgresql-operator/blob/v2.8.2/deploy/rbac.yaml ( Link to actual repo ../deploy/rbac.yaml)
- Operator watches only the namespace where it's deployed
- Multiple operator instances can coexist in different namespaces
- Provides strong isolation and security boundaries
- Minimal blast radius in case of operator failures

### Cluster-Wide Deployment

In cluster-wide mode, a single operator instance can manage PostgreSQL clusters across multiple specified namespaces. The operator uses Kubernetes `ClusterRole` and `ClusterRoleBinding` resources, which are cluster-scoped, allowing it to access resources across namespaces.

![image](./cluster-wide.png)

**Key Characteristics:**
- Uses `ClusterRole` and `ClusterRoleBinding` (cluster-scoped RBAC) https://github.com/percona/percona-postgresql-operator/blob/v2.8.2/deploy/cw-rbac.yaml ( Link to actual repo ../deploy/cw-rbac.yaml)
- Operator watches multiple namespaces specified in `WATCH_NAMESPACE`
- Requires cluster-admin privileges for RBAC setup
- Wider blast radius in case of operator failures

### Installation/Configuration

Configuration between namespace mode/cluster wide mode and the namespaces where PostgreSQL clusters are managed depends on following:
1. RBAC associated with the Operator Deployment
2. WATCH_NAMESPACE environment variable in the Operator Deployment



**Important Notes:**
- Each namespace requires its own operator instance
- Cluster names can be identical across namespaces (e.g., `cluster1` in both `percona-db-1` and `percona-db-2`)
- CRDs are cluster-scoped and shared; you don't need to install them again
- Each operator instance consumes resources independently

**Resource Comparison:**
- 2 namespaces = 2 operator Pods
- 3 namespaces = 3 operator Pods
- Each operator typically uses ~100-200Mi memory and ~100-500m CPU

**Components:**
- Operator Deployment: Runs in a dedicated namespace (e.g., `pg-operator`)
- ServiceAccount: Namespace-scoped, but bound to a ClusterRole
- ClusterRole: Grants permissions across all namespaces
- ClusterRoleBinding: Binds the ServiceAccount to the ClusterRole
- Multiple namespace informers: One per namespace in `WATCH_NAMESPACE`

### When to Use

Use cluster-wide deployment when:
- You need centralized management of clusters across multiple namespaces
- You want to reduce resource consumption (single operator vs multiple)
- You have a small number of namespaces to manage (< 10 recommended)
- You need cross-namespace operations (e.g., backup/restore between namespaces)
- You have cluster-admin privileges available for RBAC setup
- You're managing a development/staging environment with less strict isolation requirements

**Important:** The `WATCH_NAMESPACE` value must include:
- The namespace where the operator is deployed (`pg-operator`)
- All namespaces where you want to deploy PostgreSQL clusters (`percona-db-1`, `percona-db-2`, etc.)

**Complete example configuration:**

```yaml
# In deploy/cw-bundle.yaml, locate the ClusterRoleBinding section:
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: percona-postgresql-operator
subjects:
  - kind: ServiceAccount
    name: percona-postgresql-operator
    namespace: pg-operator  # Update this
roleRef:
  kind: ClusterRole
  name: percona-postgresql-operator
  apiGroup: rbac.authorization.k8s.io
---
# Locate the Deployment section:
apiVersion: apps/v1
kind: Deployment
metadata:
  name: percona-postgresql-operator
  namespace: pg-operator
spec:
  template:
    spec:
      containers:
      - name: percona-postgresql-operator
        env:
        - name: WATCH_NAMESPACE
          value: "pg-operator,percona-db-1,percona-db-2"  # Update this
```

## Security Considerations

### Namespace-Scoped Security

**Advantages:**
- Principle of least privilege: Operator only has access to its namespace
- Namespace-level isolation prevents cross-namespace access
- Easier to audit and comply with security policies
- Reduced attack surface per operator instance

**Considerations:**
- Each operator requires separate RBAC configuration
- More ServiceAccounts to manage

### Cluster-Wide Security

**Advantages:**
- Single point of RBAC management
- Easier to maintain consistent permissions

**Risks:**
- Operator has cluster-wide permissions (via ClusterRole)
- Compromise of operator Pod affects all watched namespaces
- Requires cluster-admin privileges for setup
- Larger blast radius in case of security incidents

**Best Practices:**
- Deploy operator in a dedicated, restricted namespace
- Use NetworkPolicies to limit operator Pod network access
- Regularly audit ClusterRole permissions
- Monitor operator Pod for suspicious activity
- Use Pod Security Standards/Policies to restrict operator capabilities


```bash
# 1. Check operator Pod is running
$ kubectl get pods -n pg-operator

# 2. Verify ClusterRole and ClusterRoleBinding
$ kubectl get clusterrole,clusterrolebinding | grep percona-postgresql-operator

# 3. Check WATCH_NAMESPACE configuration
$ kubectl get deployment percona-postgresql-operator -n pg-operator -o jsonpath='{.spec.template.spec.containers[0].env[?(@.name=="WATCH_NAMESPACE")].value}'

# 4. Check operator logs for watched namespaces
$ kubectl logs -n pg-operator -l name=percona-postgresql-operator | grep -i "watch\|namespace"

# 5. Verify operator can access multiple namespaces
$ kubectl auth can-i get perconapgcluster --namespace=percona-db-1 --as=system:serviceaccount:pg-operator:percona-postgresql-operator
$ kubectl auth can-i get perconapgcluster --namespace=percona-db-2 --as=system:serviceaccount:pg-operator:percona-postgresql-operator
# Both should return "yes"
### Common Issues and Solutions

#### Issue 1: Operator Cannot Create Resources

**Symptoms:**
- Operator Pod is running but clusters are not being created
- Error messages about permissions in operator logs

**Diagnosis:**
```bash
# Check operator logs
$ kubectl logs -n <namespace> -l name=percona-postgresql-operator

# Check RBAC resources
$ kubectl get role,rolebinding -n <namespace>  # For namespace-scoped
$ kubectl get clusterrole,clusterrolebinding | grep percona  # For cluster-wide
```

**Solution:**
- Verify RBAC resources are correctly applied
- For namespace-scoped: Ensure Role and RoleBinding exist in the namespace
- For cluster-wide: Ensure ClusterRole and ClusterRoleBinding exist and reference correct ServiceAccount

#### Issue 2: Operator Not Watching Expected Namespaces

**Symptoms:**
- Clusters in some namespaces are not being managed
- Operator logs don't show expected namespaces

**Diagnosis:**
```bash
# Check WATCH_NAMESPACE value
$ kubectl get deployment percona-postgresql-operator -n pg-operator -o yaml | grep -A 5 WATCH_NAMESPACE

# Check operator logs
$ kubectl logs -n pg-operator -l name=percona-postgresql-operator | grep -i "watch"
```

**Solution:**
- Ensure `WATCH_NAMESPACE` includes all target namespaces
- For cluster-wide: Include operator's own namespace in the list
- Restart operator Pod after changing `WATCH_NAMESPACE`

#### Issue 3: Cross-Namespace Operations Fail

**Symptoms:**
- Backup/restore operations between namespaces fail
- Error messages about namespace access

**Diagnosis:**
```bash
# Check if using namespace-scoped operator (which cannot access other namespaces)
$ kubectl get role -n <namespace> | grep percona  # If exists, it's namespace-scoped
```

**Solution:**
- Use cluster-wide deployment for cross-namespace operations
- Or perform operations within the same namespace

#### Issue 4: Operator Pod CrashLoopBackOff

**Symptoms:**
- Operator Pod continuously restarts
- Error logs in operator Pod

**Diagnosis:**
```bash
# Check Pod status
$ kubectl describe pod -n <namespace> -l name=percona-postgresql-operator

# Check recent logs
$ kubectl logs -n <namespace> -l name=percona-postgresql-operator --previous
```

**Common Causes:**
- Invalid `WATCH_NAMESPACE` format (spaces, invalid characters)
- Missing or incorrect RBAC configuration
- ServiceAccount not found
- CRDs not installed

**Solution:**
- Verify `WATCH_NAMESPACE` format (comma-separated, no spaces)
- Re-apply RBAC resources
- Ensure CRDs are installed: `kubectl get crd | grep percona`

## Best Practices

### Namespace-Scoped Deployment

1. **Use dedicated namespaces** for each team/environment
2. **Apply ResourceQuotas** to limit resource consumption per namespace
3. **Use NetworkPolicies** to enforce network isolation
4. **Monitor each operator** independently
5. **Use consistent naming** for operator resources across namespaces

### Cluster-Wide Deployment

1. **Limit watched namespaces** to < 10 for optimal performance
2. **Use dedicated operator namespace** separate from cluster namespaces
3. **Document all watched namespaces** in `WATCH_NAMESPACE`
4. **Monitor operator resource usage** as namespaces are added
5. **Regularly audit ClusterRole permissions**
6. **Use Pod Security Standards** to restrict operator capabilities
7. **Implement NetworkPolicies** to limit operator network access
